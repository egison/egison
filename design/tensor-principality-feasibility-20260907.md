# テンソル補完の一般化後における証明の見通し

2026-09-07．実装・既存の Lean ソース・追加の小さな実行例を調べた設計検討である．この文書は新しい証明の完成を報告するものではない．今回，処理系の修正は行っていない．

## 結論

推論した型と包装後の型を一致させ，任意個数の引数へ補完を一般化したことにより，最終的な型付き構文木からの挿入を証明する構成は明確になった．ただし，現行実装全体の健全性・完全性・主要型性は，そのまま証明できる状態ではない．追加の実行確認で，型情報が失われる例と，本来型付けできる式を拒否する例が見つかった．

主要型性とは，同じ仕様が同じ式に認める任意の型が，推論結果の型変数への代入で得られることである．正規化は型比較に含めるが，階数0としての受入れを型の等しさと混同しない．「実装の選択が決定的」「挿入後の実行結果が正しい」は，それぞれ主要型性とは別の性質である．

新しい持ち上げ制約を型スキームに追加しない方針を維持する．let 多相，高階関数，`ones`，`sum`，テンソル正規化を含む全体の定理を目標とし，反例のある構文を除外して対処しない．一方で，主要型性の中心補題が成立することはまだ確認できておらず，任意個数への一般化だけから「証明できる」とは断定できない．

## 1. 実装上の反例：複数の高階引数の照合順序

次の二つの高階関数は，引数の並びだけが異なる．

```egison
def probeConstant (x : Integer) : Integer := 1
def probePredicate (x : Integer) : Bool := True

def probeMapFilter f p xs := map f (filter p xs)
def probeFilterMap p f xs := map f (filter p xs)

def probeMapFirst xs := probeMapFilter probeConstant probePredicate xs
def probePredicateFirst xs := probeFilterMap probePredicate probeConstant xs
```

現行実装では，`probeMapFirst` の定義が `Tensor Bool` と `Bool` の照合エラーになる．一方，`probePredicateFirst` は `[Integer] -> [Integer]` と推論される．`probeMapFilter probeConstant probePredicate [1,2]` と，`probePredicateFirst [1,2]` はともに `[1,1]` を返す．

原因は次のとおりである．

1. `probeMapFilter` の型は `(a -> b) -> (a -> Bool) -> [a] -> [b]` である．未知の `xs` だけでは `a` は確定しない．
2. `probeConstant` を先に調べると，期待する引数型・戻り値型がともに未確定なので，補完によって `a` と `b` を `Tensor Integer` にする．
3. その後の `probePredicate` は `Tensor Integer -> Bool` を要求される．成分ごとに適用すれば戻り値は `Tensor Bool` となり，`filter` が要求する `Bool` と合わない．
4. 述語を先に調べる場合は，固定された戻り値型 `Bool` により補完されず，共通の入力型が `Integer` に決まる．残りの照合も成功する．

この例には通常の多相型推論でも得られる `[Integer] -> [Integer]` という型がある．したがって，これは現行推論器の完全性（仕様が認める式を必ず受理する性質）の問題であり，この式に主要型が存在しない例ではない．

修正方針は，特定の述語だけを先に処理することではなく，**一つの関数適用にある全引数の確定済みの要求を伝播させてから，未確定の位置の補完を決めること**である．固定されたスカラー結果，明示された Tensor，型変数の共有，関数の引数と結果の対応をまとめて扱う．内部で再検査する処理は可能だが，型スキームに新しい残余制約を保持する設計にはしない．

証明では，各伝播が仕様上の解を失わないこと，伝播が停止すること，残った位置の補完が処理順序に依存しないことを示す必要がある．この順序変更だけで全体の主要型性が従うわけではない．

関連実装：[checkApplicationArguments](../hs-src/Language/Egison/Type/Infer.hs:5580)，[callbackLiftMask](../hs-src/Language/Egison/Type/TensorMapInsertion.hs:243)．

## 2. 実装上の反例：リスト連結の結果型

```egison
[1] ++ [[|2,3|]]
[[|2,3|]] ++ [1]
```

型付き構文木の出力で確認した結果は次のとおりである．

| 式 | 現行の推論型 | 実行結果 |
|---|---|---|
| `[1] ++ [[|2,3|]]` | `[Integer]` | `[1, [|2,3|]]` |
| `[[|2,3|]] ++ [1]` | `[Tensor Integer]` | `[[|2,3|], 1]` |

最初の結果は階数1のテンソルを要素に含むため，`[Integer]` は正しくない．方向を持つ階数0の受入れの下では，両方とも `[Tensor Integer]` とすべきである．これは健全性（推論結果が仕様上の正しい型付けである性質）の問題である．実行が停止せず値を返したことは，その値に記録された型が正しいことを意味しない．

[IJoinExpr の処理](../hs-src/Language/Egison/Type/Infer.hs:2146)は，従来の単一化で両側を照合し，左側の型を結果に使っている．関数適用に導入した区別が，ここには行き渡っていない．

リスト生成・連結・条件分岐など，複数の式を共通の型にまとめる箇所にも規則が必要である．`Integer` と `Tensor Integer` の共通の型を `Tensor Integer` とし，リストの内部にある Tensor をその位置で保つ．リスト生成・条件分岐にも従来の単一化を使う経路があることはソースで確認したが，上表の実行確認は連結の二例について行ったものである．

共通の型を選ぶ規則は，関数の引数位置では型の受入れの向きが逆になることも含めて検討する．単に構文木の各位置で Tensor を付け足す処理とはしない．

## 3. 主要型性の中心に残る数学的な課題

`N` を `Tensor (Tensor a) = Tensor a` を適用する正規化とする．

```text
N(Tensor a) = Tensor Integer
```

には，少なくとも次の二つの解がある．

```text
a := Integer
a := Tensor Integer
```

通常の型構文では，この方程式に最も一般的な単一の単一化代入はない．解の `a` の正規形は `Integer` または `Tensor Integer` に限られ，いずれも型変数を含まないため，後の代入で他方を得られない．未確定の型変数を残しただけでは方程式の解になっていない．

この差は，たとえば `forall a. Tensor a -> a` の `a` が戻り値にも現れる場合に観測される．二つの具体化は，正規化後にそれぞれ次になる．

```text
Tensor Integer -> Integer
Tensor Integer -> Tensor Integer
```

既存の [collapse_var_witness](/Users/egisatoshi/PL/type-tensor-mech/TypeTensor/Elaboration/Inference/AlgorithmComplete.lean:2280) は，二番目の具体化が後続の型付けに必要になる宣言的導出と，従来の推論核による拒否を記録している．これは現在の Egison で同じ式が拒否されると確認したものではなく，機械化側の正規化・具体化の問題を示す根拠である．

**したがって，通常の Hindley–Milner 推論の証明に「正規化してから単一化する」と付け足すだけでは不十分である．** 全式の主要型性を否定するには，同じ目標仕様における導出と，その全体の型の比較まで必要であり，方程式の反例だけから不可能とは結論しない．

最初に確かめるべき中心命題は，次である．

> 共通の Tensor 型への補完と方向を持つ受入れを含む仕様の任意の型付けについて，推論結果の型と環境への代入を経由して，同じ型付けの型と環境を得られる．

型だけでなく環境も含めるのは，関数定義の外側にある未確定の型変数を推論が勝手に確定し，必要な解を失わないことを示すためである．型構造の照合と Tensor を付ける位置の決定を分けて証明することは候補になるが，この命題の成立を保証するものではない．上記の二つの具体化を含め，仕様上必要な解をすべて扱えて初めて十分である．

定義経由の `ones [1,2] : [Tensor Integer]` と，直接の `map constant [1,2] : [Integer]` は異なる入力式なので，その型が異なること自体は主要型性の反例ではない．また，推論で得る型と，その型を期待型として受け入れる判断，生成後の式が持つ追加的な型を区別する．この区別によって，必要なプログラムや多相的な使用を除外してはならない．

## 4. 挿入と型安全性についての証明方針

### 最終型だけからの挿入

推論後の型付き構文木を固定すれば，持ち上げる引数位置と生成する構文は規則によって決まる．一意性は生成変数の名前の違いを除いて述べる．これとは別に，次を証明する．

1. 推論が成功した構文木は，各高階引数の実際の型・期待型・包装後の型の対応を満たす．この条件は，挿入器が成功したという事実で定義しない．
2. その対応を満たす任意の構文木から挿入が成功し，推論結果と同じ型を持つ式を生成する．
3. let の一般化と具体化，後からの型代入が，この対応を保つ．

任意の型の組に対して持ち上げ位置が代入で不変である，とは主張できない．既存の [代入前後で判定が変わる反例](/Users/egisatoshi/PL/type-tensor-mech/TypeTensor/Elaboration/Conformance/CallbackStructuralBridge.lean:340) は維持する．代わりに，成功した推論が作る型の対応と既存の型制約を満たす代入について証明する．これは成功プログラム全体の不変条件を示す課題であり，最終型による挿入を断念したり，挿入履歴を保存したりする理由にはならない．

今回の推論側での型の反映はこの証明に必要な変更である．ただし，「同じ補助関数を推論と挿入で使う」という実装上の共有だけでは，後続の代入を経た一致まで証明できない．

### 任意個数の包装と実行

包装単体の型保存は，選ばれた引数の個数に関する帰納法で進められる見込みがある．一引数の `tensorMap`，二引数の `tensorMap2`，三引数以上で成分をタプルに集めてから関数へ渡す構成を扱う．スカラー混在と Tensor を返す関数についても，戻り値を正規化した型を結論にする．

その後，[既存の型保存・型安全性](/Users/egisatoshi/PL/type-tensor-mech/TypeTensor/Metatheory/SubjectReduction.lean:22)へ接続する．リスト・タプル，多引数の添字の対応，添字補完，検査済みの形状エラーは追加・接続が必要である．Tensor の階数0受入れは全体適用であり，成分適用の規則と区別する．

「固定された型付き構文木からの一意性」と「同じ入力式の任意の主要な型付けからの一意性」も別である．後者には，前節の主要型性と補完の選択の一致が必要になる．

## 5. 推奨する作業順

1. **二つの実装上の反例を修正し，受理・型・生成式を回帰テストにする．** 複数の高階引数をまとめた伝播と，リストなどの共通の型を選ぶ規則を実装・仕様の双方で揃える．
2. **正規化と補完を含む上記の中心命題を先に検討・機械化する．** 全体の大きな帰納証明に入る前に，通常の代入による主要型性に必要なこの点を解決する．決定性や候補の列挙で代用しない．
3. **let の一般化・具体化を接続する．** 定義の型の照合と補完を終えてから一般化し，任意の使用時の代入との関係を証明する．既存の [let の反例と代入の補題](/Users/egisatoshi/PL/type-tensor-mech/TypeTensor/Elaboration/Inference/LetTransport.lean:1)を再利用する．
4. **最終型からの挿入成功・型保存・一意性を証明する．** 固定した引数順序で生成する構文の一意性と，主要な導出間の一致を分けて接続する．
5. **添字補完を含む実行の型安全性まで結ぶ．** 同じ言語と推論器に対する定理として，論文の英語版・日本語版に証明と対応を反映する．

今回の実装の修正以前に存在した，より小さい推論器の主要型性の証明は再利用できる．ただし，[PrincipalityES.lean](/Users/egisatoshi/PL/type-tensor-mech/TypeTensor/Elaboration/Inference/PrincipalityES.lean:1)の定理をそのまま，let・高階引数・一般の正規化を含む全体の証明と読むことはできない．全体へ拡張するために不足している箇所が上記である．
