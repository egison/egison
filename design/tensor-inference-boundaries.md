# テンソルの設計仕様と実装・検証の対応

状態：**設計の整理段階．2026-11-11 の印を使う型推論は未実装・未検証である．** 言語の規則と期待結果の正本は [設計仕様](type-tensor-simple.md) とする．この文書は現行実装との差，実装・論文・Lean の対応，今後の検証対象を記す．作業順序は [移行作業](tensor-mark-types.md) にまとめる．

## 1. 現行実装との差

現行実装の説明を，新しい設計の規則として適用しない．とくに次の点が異なる．

| 対象 | 現行実装 | 決定した設計 |
| --- | --- | --- |
| 定義の利用 | 本体と制約を保持し，使用箇所ごとに定義の候補を推論・選択する | 本体を一度だけ型付けし，型・印・制約から挿入を決める |
| 関数の仮引数の使用 | 使用箇所ごとの変換を扱う | 実際の関数を渡す箇所で一度だけ決め，同じ関数と型を共有する |
| 挿入なし型付け | 入力全体の成功時は式を保存する | テンソル型の位置から決まる挿入を認め，その場合は階数 0 の入力の評価結果を保存する |
| テンソル構築式の成分 | スカラーとテンソルの混在を型エラーにする | 要素型を照合し，形状の不一致は実行時の形状エラーにする |
| 積の定義 | スカラー入力・テンソル入力の候補を持つ | テンソル入力の型と本体を一つ持ち，スカラー入力は階数 0 として受け取る |
| 型の表示 | `sum` は通常のスカラー型を表示する | `sum` は `[Integer*p] -> Integer*p` と印を表示する |
| 述語の本体 | 既知の本体の一部だけを使用先に合わせて変換できる | 直接書いたラムダ式も名前付き関数も，本体から求めた型・印・制約で扱う．受け取り側に合わせて本体の一部だけに挿入しない |
| 縮約結果への型注釈 | トップレベルで外側の `Tensor` を取り除いて照合できる | この規則を維持し，利用者の正しい注釈を前提とすることを明記する |

現在の `Infer.hs` の `searchTypingPhases` は，挿入なし型推論の成功を優先する．`buildFunctionFamily`・`instantiateFunctionRecipe` などは，定義の候補を使用時に具体化する．これらは置き換える対象であり，新設計の試作が済んだことを示すものではない．

現行の `Type/Unify.hs` は，型クラス制約を伴う照合（`TensorConstraintAware`），`Tensor a` と `a` を同一視しない厳密な照合（`TensorStrict`），トップレベルの注釈との照合（`TensorTopLevel`）を区別する．新設計でも，成分ごとの適用，階数 0 の包含，通常の型の等式，明示的な注釈との照合を混同しない．

`\g h -> (g h, h 1)` の一方の使用だけで `h` を包む現行の検査は，新設計では共有した関数と型の検査に更新する．述語の本体を使用先に合わせて変更する検査も，直接書いたラムダ式を含め，設計仕様 §5.1 の拒否例へ更新する．これらは未対応の改善課題としては残さない．

## 2. Egison・論文・Lean の関係

Egison の実装箇所は [FILE_MAPPING.md](FILE_MAPPING.md)，処理全体は [implementation.md](implementation.md) にまとめる．印の導入後も，型と挿入を決め，挿入した式の要素型に応じて型クラス辞書を展開し，評価する順序は保つ．

論文は [type-tensor-paper](../../type-tensor-paper/)，機械化された規則と証明は [type-tensor-mech](../../type-tensor-mech/README.md) にある．実行結果の照合は [実装対応文書](../../type-tensor-mech/docs/implementation-audit.md)，現在の証明の接続状況は [残課題](../../type-tensor-mech/docs/open-problems.md) と [変換条件とコード生成](../../type-tensor-mech/docs/candidate-generation.md) に記されている．これらは現行方式に対する資料であり，印を使う新設計の正しさを既に証明したものではない．

現在の Lean の `SourceSupportTraversal` は，テンソル型の位置から入力まで型の関係をたどる．この考え方を新設計のテンソル構築式の成分にも接続する．`SourceAutomaticInference` にある導出の比較，`PendingDefinitionExpansion` にある定義の候補の展開などは，印と制約に基づく規則へ置き換える対象である．

現在の `PublicInference.noInsertion_success_preserved` は，挿入なし型推論の成功から入力式の保存を示す．新設計では，設計仕様 §8 に従い，通常の場合の式そのものの保存と，テンソル型の位置から挿入する場合の階数 0 の入力に対する評価結果の保存を区別して定式化し，証明する．

Egison のライブラリは `contract : Tensor a -> [Tensor a]` を介して縮約する．論文と Lean の整数モデルの `contractWith` は基本操作であり，還元関数の型の表し方も異なる．対応を検査するときは，設計仕様 §6.2 の区別を保つ．

## 3. 検証する性質

以下は新設計に対する要件であり，証明・検査の完了を示す一覧ではない．

- **型付けの健全性**：挿入後の式とその評価結果が，規則に従う型を持つこと．トップレベルの縮約結果への注釈は，設計仕様 §7.2 のとおり利用者の正しい注釈を前提として定式化する．
- **通常の型推論の保存**：テンソル操作のないプログラムでは印をスカラーに決め，通常の型推論と同じ型を得ること．
- **完全性**：宣言的な型付け規則，つまり推論の実行手順を使わずに認める型と挿入を定める規則，に従って型付けできる式を推論できること．ユーザーが指定した新規則に合わせて，受理例と拒否例をともに定義する．
- **主要型**：新規則が選ぶ計算について，認められる型を，推論した型の型変数・印の具体化で表せること．印の制約と正規化を含む正確な言明は試作で確定する．
- **挿入の再構成**：決定した型・印・制約から，実行する式を生成できること．`foldl` と `gp` の関数引数の各使用に別々の挿入を作らないこと．
- **順序に依存しない判断**：引数を調べる順序や部分適用の括り方により，型・挿入・値が変わらないこと．外側から捕捉した型と値の共有を保つこと．
- **形状と添字の検査**：型に階数や軸長を持たせず，生成・成分ごとの適用・添字操作で定めた実行時の検査を行うこと．

論文の健全性・完全性・主要型・選択の表現力などの主張に届くよう，規則・証明・実装を更新する．機械化や実装の不足を理由に主張を縮めない．挿入位置と受理対象の変更は，利用者が指定した今回の決定として明示する．有限個の実行例の一致と，一般的な性質の証明は別々の根拠である．

## 4. 既存の検査と新設計への接続

設計仕様 §12 の例は新しい期待結果である．次のファイルは現行の検査の所在であり，まだ新設計に更新していない．検査では値だけでなく，推論型と挿入箇所も確認する．

| 検査対象 | 既存の検査 |
| --- | --- |
| 型・印・挿入，受け取り側との型の整合 | `test/TensorInference.hs` |
| 高階関数，部分適用，別名，捕捉，再帰 | `test/lib/core/tensor-higher-order.egi`，`tensor-function-families.egi` |
| リストと分岐の共通型，階数 0 の包含 | `test/lib/core/tensor-result-types.egi`，`tensor-result-admission.egi` |
| 積，テンソル型の位置からの入力の決定 | `test/lib/core/tensor-demand.egi`，`indexed-definition-constraints.egi` |
| 形状と添字，生成関数が返すテンソルの組立て | `test/lib/math/tensor.egi`，`tensor-assembly.egi` |
| 名前のない軸と添字の有効範囲，微分形式 | `test/lib/math/symbol-scopes.egi`，`mini-test/9921-appended-index-prefix.egi` |
| Lean の規則と Egison との比較 | `type-tensor-mech/tests/algebraic.py`，`local_inference.py`，`tensor_demand.py` |
| テンソル公開操作の正常結果とエラー | `type-tensor-mech/tests/egison-tensor-operations.json` |

とくに次を新設計の検査へ接続する．

- `gp` の二つの使用と `foldl` の再帰で，同じ変換済みの関数を共有すること．`gp` の右側は値が `1` でも型は `Tensor Integer` であること．
- 直接書いたラムダ式でも名前付き・保存済みの関数でも，述語の本体内の加算だけを使用先に合わせて変更する例は拒否すること．利用者が `tensorMap2` を明示した別のプログラムは受理すること．
- `tensorShape (x + 1)` がスカラー入力とテンソル入力に同じ本体を使うこと．
- テンソル構築式の成分へテンソル全体を渡すことと，形状エラーを持ち上げで回避しないこと．
- 縮約結果に利用者が正しく付けたスカラー型注釈を受け入れること．通常の型の等式では `Tensor a` と `a` を同一視しないこと．
- `sum2`，`twiceSum`，`mysum`，独立した二つの `foldl` の使用が，本体の再推論を繰り返さず，それぞれ数秒で終わること．
- `map (map (\x -> x+1)) [[1],[[|2,3|]]]` のような入れ子の適用，複数の関数引数，関数を返す式にも同じ型と共有の規則を適用できること．

リストと分岐の共通型は現在の `commonResultType`・`commonCollectionType`，テンソルの組立ては `Core.normalizeTensorWHNF`，追加添字は `refTensorWithOverride`，内部の空の配列への参照は `emptyReference` に対応する．新設計の導入時にも，これらが担う既存の振る舞いを検査する．

文書整理の段階では，処理系・テスト・論文・Lean のソースは変更しない．実装後には通常の回帰検査，代表的な数式処理の例の警告・エラー・実行時間，Lean の全検査と公理の監査を行う．
