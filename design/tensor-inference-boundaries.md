# テンソル型推論の仕様と実装の対応

## 型推論が満たす要件

統合型推論は型注釈を要求せず，テンソルが関係しない式の通常の Hindley–Milner 推論型を保つ．高階引数の変換候補は定義に保持して使用ごとに選択し，未確定な引数へのテンソルは全体のまま渡す．合法な `tensorMap` の挿入で型付けできるプログラムを受理すること，推論型から選んだ挿入を再構成できることを設計の要件とする．

主要型とは，統合型推論が選択する計算について，優先規則が認める型を，推論した型の型変数への代入で表せる型である．型の正規化は比較に含めるが，スカラーを階数0として受け取ることと，型が等しいことは区別する．

Lean の規則と証明は [type-tensor-mech](../../type-tensor-mech/README.md)，実行による照合は [実装対応文書](../../type-tensor-mech/docs/implementation-audit.md) にまとめる．Haskell 実装との有限の比較と，独立した型規則に対する一般定理は別々の根拠である．

## 挿入なし型推論と自動挿入型推論を統合する

挿入なし型推論は，書かれた式にテンソル操作や高階引数の変換を追加せずに型を求める．明示した `tensorMap`・`tensorMap2` は使える．自動挿入型推論は，それらの追加や高階引数の変換を許し，型と実行する式を求める．どちらも型注釈を要求しない．

統合型推論は，まず入力式全体について挿入なし型推論を試し，失敗した場合に自動挿入型推論へ進む．部分式を先に確定せず，後続の適用と let の使用に応じて型の候補を選び直す．

```egison
(\f -> let ys := tensorMap f [|1,2|] in f [|1,2|]) (\x -> 0)
-- Integer，結果 0
```

この式は `f : Tensor Integer -> Integer` として挿入なし型推論が受理する．明示的な写像は各成分に `f` を適用し，最後の適用はテンソル全体を渡す．`f : Integer -> Integer` を選んで最後の適用に写像を追加する計算は，自動挿入型推論の別の候補である．一方，`(\f -> f [|1,2|]) (\x -> let y := x+0 in 0)` には自動挿入が必要で，結果は `[|0,0|]` となる．

`Infer.hs` の `searchTypingPhases` は，式とトップレベル定義を同じ順序で検査する．挿入なし型推論では，写像を伴う適用，関数引数の自動変換，自動生成した定義の変換候補を使わない．整数の添字用に具体化した関数へ数学記号を渡す場合も，挿入なし型推論の成功とはしない．各処理の失敗時には，型代入と共有制約を検査前へ戻す．自動挿入型推論は，変換後の型と内部制約を候補間で比較する．明示的な `tensorMap` の成分型には，スカラーだけでなくテンソル型も許す．

`test/TensorInference.hs` は期待型を入力せず推論された型を検査し，`test/lib/core/tensor-higher-order.egi` は評価結果を検査する．Lean の `PublicInference.noInsertion_success_preserved` は，実際の挿入なし型推論の成功から，統合型推論の成功と入力式の保存を証明する．型規則が許すすべての自動変換を実際の候補生成へ接続し，統合型推論の成功を示すために残る証明は，[残課題](../../type-tensor-mech/docs/open-problems.md) に記す．

## 複数の高階引数の照合

同じ入力型を共有する複数の関数を渡す場合は，全引数の固定された要求を満たしてから補完する必要がある．次の例の述語 `positive` はスカラー比較の結果そのものを返す．比較を写像すると結果が `Tensor Bool` になるため，共有する入力にはスカラーの要求がある．

```egison
def increment x := x+1
def positive x := x > 0
def mapFilter f p xs := map f (filter p xs)
def filterMap p f xs := map f (filter p xs)

\xs -> mapFilter increment positive xs
\xs -> filterMap positive increment xs
```

どちらの式も，テンソルの要求がない場合は `[Integer] -> [Integer]` と推論する．変換候補では，述語の固定された結果 `Bool` と，両方の関数に共有された入力型を一緒に照合する．引数の記述順によって結果を変えない．テンソル全体を受け取って `Bool` を返す述語なら，写像する関数だけをテンソル対応にできる．

定義の各参照には独立した候補選択を置く．型と内部制約を一緒に具体化し，後続の引数や高階引数の不一致に応じて選び直す．捕捉した値と単相な型の関係は共有し，ソースの実行を候補比較には使わない．

## リストと分岐の共通型

```egison
[1] ++ [[|2,3|]]
[[|2,3|]] ++ [1]
```

どちらの式も `[Tensor Integer]` と推論する．スカラーは階数0として受け取り，テンソルの要素型の情報を保つ．リスト構築，先頭への追加，連結，条件分岐は，共通の結果型を求める `commonResultType` を使う．リストとタプルの内部でもテンソルの位置を保ち，未確定な要素の型は，具体的な成分から求めた共通型と照合する．`commonCollectionType` は，連結の両辺と先頭追加の末尾がリストであることも検査する．関数やその他の型構成子の内部のテンソルは，型の照合のために消去しない．

`test/TensorInference.hs` は推論型と挿入を，`test/lib/core/tensor-result-types.egi` は値と，推論型に基づく後続の写像を検査する．

スカラーを階数0として受け取る場合は，その値の型 `a` を `Tensor a` と等しくする代入を要求しない．型の等式として `a = Tensor a` が生じた場合は，正規化 `Tensor (Tensor b) = Tensor b` に従い，`a := Tensor b` という解を構成する．リストなどを介して自分自身を含む型は，循環する型として拒否する．

## 添字と実行時の形状

型 `Tensor a` は階数や軸長を持たない．生成，保存配列，写像の組立ては実行時に形状と添字の一致を検査する．スカラーとテンソルを混在させるリテラルについても，Egison と Lean の受理には差がある．対象と必要な接続は [実装対応文書](../../type-tensor-mech/docs/implementation-audit.md) と [残課題](../../type-tensor-mech/docs/open-problems.md) を参照する．

## 使用時の型の具体化と候補の生成

関数を供給する位置では，元の型と受け取り側の型を別々に保持する．共有する引数，返り値，高階引数の制約を解き，恒等変換または成分ごとの写像を選ぶ．使用時に関数となる返り値も扱い，変換の引数の個数を定義時に固定しない．テンソルを消去した型の構造は，候補の引数の個数を求めるためにだけ使う．実際の型の照合と成分の検査は，テンソルを含む型全体で行う．

一般化した変数と内部型は使用ごとに同じ対応で新しくし，捕捉した単相な型と値は共有する．別名は元の候補群を引き継ぐ．ローカル定義は依存関係ごとに一般化し，互いに再帰する定義は単相な型を共有する．

`test/TensorInference.hs` は，`\g h -> (g h, h 1)` の返り値が使用時に関数型となる場合を含め，自動変換，逆の引数順，別名，再帰，独立した多相な使用，外部の多相な関数を検査する．受け取り側の要求に従って `g (\x y -> tensorMap2 h x y)` を生成し，`h 1` は通常の部分適用を保つ．閉じた再現ソースと機械化の状態は [変換条件とコード生成](../../type-tensor-mech/docs/candidate-generation.md) に記す．
