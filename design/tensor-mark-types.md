# 印を使うテンソル型推論への移行作業

状態：**設計の確認中．実装・試作には未着手．** 2026-11-11 の決定を [設計仕様](type-tensor-simple.md) に統合した．この文書は，設計を確認した後に行う作業と未完了事項だけを扱う．現行実装との差と検証の対応は [仕様と実装の対応](tensor-inference-boundaries.md) に記す．設計仕様の規則と例をここに重複して定義しない．

## 1. 現在の段階と作業順序

現在は，利用者が設計全体を意図どおりか確認する段階である．この段階では，Egison の実装とテスト，論文，Lean のソースを変更しない．以降は，前の段階の確認・検証を終えてから次へ進む．

1. 設計仕様の型・挿入箇所・期待結果を確認する．
2. リポジトリの外で型推論と挿入を試作し，形式的な規則と制約を解く手順を確定する．
3. Egison の型推論と挿入を更新し，回帰検査を行う．
4. 論文の英語版と日本語版を同じ内容へ更新する．
5. Lean の規則・推論・証明を更新し，Egison と比較する．
6. 文書の実装状況と用語を確認し，移行が完了したらこの文書を削除する．

印の英語名と論文の記法は未決定である．日本語の設計仕様では，当面「印」と `τ*p` を使う．この記法の判断と，既に決まった動作の採否を混同しない．

## 2. 試作で確定する技術的事項

対象は，Lean のデータ言語の範囲であるラムダ，`let`，適用，算術，テンソル構築式，`tensorMap`・`tensorMap2`，`contractWith`，添字参照，リスト，データ構成子，`case` とする．トップレベルの型注釈と型クラスへの接続も，Egison へ移す前に確認する．

- 印の間の制約の表現と解法．結果だけに現れる印を引数の印の `∨` で表す手順，整理できない関係の表し方．
- 設計仕様 §3–4 の規則を，引数や制約を調べる順序によらず解く方法．入れ子の印と，印のないスカラー仮引数への最小の持ち上げを区別すること．
- 再帰と `let` の一般化．`foldl` の初期値・リスト要素・結果に同じ印を導き，スカラーの初期値や要素を階数 0 として受け取ること．変換済みの関数を再帰呼び出しへそのまま渡すこと．
- 利用者が渡す挿入前の関数型と，高階関数の本体が受け取る挿入後の関数型の表現．通常の関数型の等式と区別し，共有する制約を実際に関数を渡す箇所へ伝えること．
- `gp`，部分適用，別名，関数を返す式で関数と型の共有を保つこと．関数の仮引数の各適用や，他の高階関数へ転送する各箇所で，別々の挿入を選ばないこと．
- 直接書いたラムダ式も，名前付き・保存済みの関数と同じく，本体から求めた型・印・制約で受け取り側と照合する手順．受け取り側に合わせて本体の一部だけへ挿入する機能は要求しない．本体自身のテンソル操作から決まる挿入や，記録した印の決定とは区別する．
- テンソル型の位置からの挿入と，それ以外の挿入なし型付けの保存との関係．階数 0 の入力に対する評価結果の保存を定式化すること．
- 型クラス制約を伴う型変数への印．例えば加算ではテンソルのインスタンスを要求せず，要素型の加算を使うこと．
- 利用者の正しいトップレベル注釈を前提に，縮約結果の `Tensor Integer` と注釈した `Integer` を照合する規則．印を消した型との照合と区別すること．

設計仕様の型の一覧と §12 の全例，Lean の既存の `tests/algebraic.py`・`tests/local_inference.py`・`tests/tensor_demand.py` の例で，型・生成する式・値を比較する．意図した変更は，仕様と実装の対応 §1 に従って分類する．利用者が指定した変更以外の差が残る間は，処理系の変更へ進まない．形式化で不明な点が分かった場合は，期待結果を勝手に変えず，規則との関係を明らかにする．

## 3. Egison

詳細なファイル対応は [FILE_MAPPING.md](FILE_MAPPING.md) に集約する．

- 型・代入・単一化に，印とその正規化，印の間の制約を加える．
- 定義の本体を一度だけ型付けし，共有する型と制約を記録する．`buildFunctionFamily`・`instantiateFunctionRecipe`・`FunctionRecipe` による使用時の本体の再推論を廃止する．
- テンソル型の位置に構築式の成分を加え，そこから型が決まる仮引数を `Tensor` 型にする．
- `buildCallbackLiftPlan`・`typeDirectedTensorLiftTypes`・`callbackLiftMask`・`wrapWithTypeDirectedTensorLift` は，実際に渡す関数を一度だけ包む処理として整理する．未確定の関数の仮引数の各適用には別の挿入を作らない．
- 印によって挿入が変わる定義だけ，確定した印ごとの本体を生成し，同じ組合せには同じものを使う．積や `tensorShape` の例は固定した一つの本体にする．
- テンソル構築式の成分を `Tensor` で包んで照合し，形状の不一致は実行時に検査する．
- 印つきの型を表示する．トップレベルの注釈の照合規則を維持する．
- 仕様と実装の対応 §4 の検査を新しい期待結果へ更新する．受理する例に加え，直接書いたラムダ式を含め，述語の本体の一部だけを受け取り側に合わせて変更する例の拒否も検査する．

Egison の `cabal test`，`mini-test` の全件，`sample/math` の代表例を検査し，警告・エラー・速度低下がないことを確認する．Haskell 系の独立したビルド・テストを同時に起動しない．`sample/` と `lib/` で値が変わる箇所は，新しい仕様に従う変更として一覧にして確認する．

## 4. 論文

英語版と日本語版を同じ内容に保ち，それぞれのディレクトリで `make` を使ってビルドする．健全性，通常の型推論の保存，完全性，主要型，選択の表現力の主張に届くよう，規則・実装・機械化を更新する．不足を理由に主張を縮めない．今回利用者が指定した挿入・型・受理対象の変更は明記する．

- 序論と Egison の説明では，スカラー関数への持ち上げを保ち，型の印とテンソル全体を受け取る関数を定義してから使う．
- 型付けの例では，テンソル構築式の成分，`foldl` の共有する印，実際の関数を渡す箇所での挿入，`gp` の右側のテンソル型を説明する．
- `sum` は印つきの型，積は一つのテンソル入力の型と階数 0 の包含で説明する．複数の定義の候補を比較する説明を，新規則へ置き換える．
- 挿入なし型付けについて，式そのものを保存する場合と，テンソル型の位置から挿入して階数 0 の入力の評価結果を保存する場合を区別する．
- 宣言的規則と推論の両方に印を導入する．利用者が書く関数型と挿入後に受け取る関数型の関係を明記する．
- 本文・付録・図表の例を設計仕様に合わせる．例の出力は新設計に対応した処理系で取り直し，更新前の出力を新設計の確認結果として使わない．

## 5. Lean

Egison と論文で規則を確定した後に行う．

- 印つきの型，印の決定，渡す関数への一度だけの挿入を，宣言的規則と推論に定義する．必要な定義には印の値ごとの本体を生成する．
- 定義の候補の展開（`PendingDefinitionExpansion`），導出の列挙と比較（`SourceSupportSpecification.candidates`，`SourceAutomaticInference.usageKey`・`choose`），`FamilyInference.finish` の該当部分を置き換える．
- 型の位置から根拠を調べる `SourceSupportTraversal` を新規則へ接続し，構築式の成分を含める．
- 設計仕様 §8 の二種類の保存を定式化し，証明する．ほかの論文の定理は，主張を維持したまま新規則で証明し直す．トップレベル注釈の前提は Egison との対応で明記する．
- 設計仕様 §12 と仕様と実装の対応 §4 を検査へ接続する．`tests/local_inference.py` で Egison と比較する．
- `make test` の全件と，全定理の公理の監査を行う．

## 6. 移行の完了条件

- 設計仕様の型の一覧と全例が，Egison と Lean で期待する型・値・挿入箇所になる．
- `foldl`・`gp` の本体が同じ変換済み関数を共有し，定義の使用ごとに本体を推論し直さない．再帰・繰り返しの使用の例が，それぞれ数秒で終わる．
- 比較検査の意図しない差がなく，Egison の回帰検査・代表例と Lean の全検査が通る．Lean に `sorry` と追加の公理がない．
- 論文の英語版と日本語版が同じ内容で，例・規則・証明と処理系が一致する．
- 設計仕様，実装との対応，ファイル対応，用語集に実装状況を反映し，旧方式の説明を新規則の説明と混在させない．
- 移行作業がなくなったら，この文書を削除し，索引から外す．
