## 実装結果

- `ones xs := map constant xs` は `[Tensor Integer] -> [Tensor Integer]` を持ち，`ones [[|1,2|]]` は `[[|1,1|]]` を返す．スカラー呼び出しも可能で，報告型は `[Tensor Integer]` のままになる．直接の `map constant [1,2]` は `[Integer]` を保つ．
- `sumElements xs := foldl1 (+) xs` は `{AddSemigroup a} [Tensor a] -> Tensor a` を推論する．型推論が包装の入力・結果型を受け手へ反映し，定義の一般化前に一致させる．後段だけの二引数用補完は除去した．
- 期待引数が未確定の場合，既存のクラス制約のもとで Tensor へ具体化でき，渡された関数の対応引数がスカラーであり，期待結果も Tensor を許す位置を補完する．既知の Tensor 入力がある場合はその位置からの伝播を優先する．固定された `Bool` 述語や，スカラー専用の期待型変数を無条件に Tensor へ変えない．

- 適用の型検査では，正規化後の厳密な等しさ，向きのある階数0の受入れ，実引数の外側での成分ごとの適用を分けた．リスト内部の Tensor を消して結果全体を Tensor で包む処理は行わない．

- `let` の束縛を依存関係の順に検査し，各定義の推論直後に仮の型を結び付ける．別名で渡すスカラー関数が，依存する定義の推論時まで未確定のまま残る問題を直した．前方参照も検査する．

## 1. 現状：三つの異なる経路がある

### 1.1 使用箇所に Tensor が見える場合

```egison
def constant (x : Integer) : Integer := 1
map constant [[|1, 2|]]
```

この例は，修正後には `[[|1, 1|]] : [Tensor Integer]` となる．引数の部分式を推論した後，テンソルを含むデータ引数の型を高階引数の期待型へ反映し，包装後の戻り値型も照合する．包装とは，ここでは `constant` を `\x -> tensorMap constant x` のような関数に変換することである．式の生成は推論後に行う．

型に基づく一引数・多引数の挿入は6月から存在する．この経路は現在も利用でき，今回の改善で再実装する必要はない．

### 1.2 定義時に Tensor が見えない場合

```egison
def ones xs := map constant xs
ones [[|1, 2|]]
```

`ones` は `[Integer] -> [Integer]` と推論され，内部の `constant` は包装されない．呼び出すと `[1]` を返し，呼び出しの型は `Tensor [Integer]` と記録される．目標の `[[|1, 1|]] : [Tensor Integer]` とは値も型も異なる．定義済みの本体へ，後続の呼び出しの型情報が戻る構成ではない．

一方，`sum xs := foldl1 (+) xs` は，定義時の型に Tensor が現れなくても，二引数用の補完により `+` を `tensorMap2` で包む．スカラー・テンソル双方の実行は成功する．ただし，挿入後の内部表現には `foldl1` の期待型 `a -> a -> a` と，包装の型 `Tensor a -> Tensor a -> Tensor a` が並ぶ．この成功を，通常の関数型の一致まで保証できているという意味には扱えない．

二引数用の補完には，次の制限がある．

- 正確に二引数であることを要求する．
- 期待型の全成分が具体的な非数式スカラー型なら補完を省く．
- 関数適用から得た式を，この補完経路から除く．型に基づく挿入経路は，部分適用したスカラー関数も既に扱える．

したがって，対象を任意個数にする変更だけでは不十分である．とくに `ones` は，定義内部の期待型が `Integer -> Integer` でも，使用時には Tensor が渡る例である．

### 1.3 明示的な tensorMap の推論にも不整合がある

今回の追加確認で，明示的な操作にも次の問題を確認した．

```egison
def toBool (x : Integer) : Bool := True
def toBool2 (x : Integer) (y : Integer) : Bool := True
```

| 式 | 現行の推論型 | 実行結果 | 正しく求める型 |
|---|---|---|---|
| `tensorMap toBool 1` | `Integer` | `True` | `Bool` |
| `tensorMap2 toBool2 1 [\|2,3\|]` | `Integer` | `[\|True,True\|]` | `Tensor Bool` |
| `tensorMap2 toBool2 [\|2,3\|] 1` | `Tensor Integer` | `[\|True,True\|]` | `Tensor Bool` |
| `tensorMap2 toBool2 [\|1,2\|] [\|3,4\|]` | `Tensor Bool` | `[\|True,True\|]` | `Tensor Bool` |

`f x := tensorMap toBool x` は，現在 `forall a. a -> a` と推論されてしまう．引数がスカラーまたは未確定の場合に，関数の戻り値を調べず，引数の型を結果型に使っていることが原因である．二引数版は，両方が Tensor の場合以外に第一引数の型を使っている．

これは包装の任意個数への一般化と独立に修正でき，先に直すべき基本規則である．評価器は既に，スカラーなら通常適用，混在する場合なら Tensor 側の成分ごとの適用を実行している．

## 2. 改善案：正規化・受入れ・持ち上げを分ける

### 2.1 型の正規化

`Tensor (Tensor a)` を `Tensor a` にまとめる．`Integer` と `Tensor Integer` を等しい型にする操作ではなく，`Tensor [Integer]` を `[Tensor Integer]` に移す操作でもない．式への挿入は伴わない．

型への代入後にも必要な正規化を行い，宣言型・部分式の型・包装の型を同じ形で比較する．ただし，`Tensor a = Tensor Integer` の主要な解をどう求めるかは別の中心課題である．両辺から Tensor を取り除く現在の単一化が，正規化の下のすべての解を表すとは仮定しない．単一化は，型変数への代入で二つの型を一致させる処理である．

### 2.2 スカラーを階数0として受け取る規則

実際の引数 `Integer` を，期待型 `Tensor Integer` の位置で使えるようにする．この向きでは，受け手の関数への成分ごとの適用は挿入しない．関数が宣言している戻り値型も勝手に変更しない．

```text
f : Tensor Integer -> Integer
f 1 : Integer

g : Tensor Integer -> Tensor Integer
g 1 : Tensor Integer
```

`g` が常にベクトルを返す関数かもしれないため，入力がスカラーだからという理由で，戻り値の Tensor を取り除いてはならない．この違いは今回の確認例でも検査した．

リストやタプルでは，安全に成分の受入れ関係を広げられる型構成子について，内部の階数0の受入れを認める．たとえば `[Integer]` を `[Tensor Integer]` として使えるようにする．これは `[Tensor Integer]` を `[Integer]` に戻す規則ではない．関数の引数位置や `IORef` などへ，同じ向きの関係を無条件に再帰適用しない．

### 2.3 成分ごとの適用

実際の引数が `Tensor a` で，受け手の対応する引数を既存の型・型クラス制約からスカラーと判断できる場合に，`tensorMap` などを挿入する．型クラス制約とは，加算などの演算をその型で利用できることを要求する既存の仕組みである．

```text
f : Integer -> Bool
f [|1,2|]  ==>  tensorMap f [|1,2|] : Tensor Bool
```

戻り値型は，生成する適用から計算する．実装上の「どこかで Tensor を取り除いた」という真偽値だけから，結果全体へ Tensor を付けない．

```egison
def singleton (x : Integer) : [Integer] := [x]
singleton [|1,2|]             -- [|[1],[2]|] : Tensor [Integer]
map constant [[|1,2|]]        -- [[|1,1|]]  : [Tensor Integer]
```

前者は `singleton` の適用全体を成分ごとに行う．後者は `map` に渡す関数を持ち上げるので，`map : (a -> b) -> [a] -> [b]` の `b` に `Tensor Integer` が入り，リストの内側に Tensor が残る．この型の位置の違いを，同じ仕様と型計算から導く．

実装では，型の等式を解く処理，方向を持つ引数の受入れ，持ち上げ後の関数型の計算を分ける．局所的な処理結果として，代入と適用後の型を返せばよく，新しい未解決の条件を型スキームへ蓄積する必要はない．最終的な式の生成は，引き続き推論後の型から行う．パターンマッチ側の型照合を，テンソル適用専用の規則で置き換えない．

## 3. 明示的な tensorMap の型計算を先に整える

`tensorMap` と `tensorMap2` は，どの分岐でも関数の引数型と戻り値型を調べる．

| 呼び出し時に分かる入力 | 型計算 |
|---|---|
| 全てスカラー | 各引数を関数の引数型と照合し，その関数の戻り値型を返す |
| 一つ以上が Tensor | 対応する成分型を関数の引数型と照合し，戻り値型を Tensor で包んで正規化する |
| 型が未確定 | 関数型との関係を作って推論する．引数型を結果型へ流用しない |

型が未確定の場合の共通の型として，`tensorMap f` に `Tensor a -> Tensor b` を与える案を検討する．既存の階数0の受入れでスカラーも渡せる．この案の型の精度については次節で明記する．

挿入後のコアにも，全引数がスカラーと分かる場合に通常の戻り値型を与える規則が必要である．実行時の通常適用と対応させ，型保存を証明する．型ラベルだけを都合よく変更して済ませない．

## 4. 任意個数の補完を，推論時の型計算と共有する

### 4.1 変換する式

スカラーとして成分ごとに処理する位置を，元の関数の型と既存のクラス制約から選ぶ．Tensor 全体を受け取る位置，無制約の型変数の位置，既存の規則で対象外の制御・資源の型は，それだけを理由に持ち上げない．

- 一引数：`f` を `\x -> tensorMap f x` にする．
- 二引数：既存の `\x y -> tensorMap2 f x y` を使う．
- 多引数・混在：選んだ位置について既存の任意個数の式生成処理を使う．共有添字の対応を保つことは検証・証明する．
- 部分適用：得られた関数の型に基づいて判定する．式が関数適用であるという構文だけで除外しない．式の共有と評価順は，既存の関数・let の意味に合わせる．

引数が実際に Tensor と分かる場合の変換と，定義時にまだ分からない場合の補完は，同じ包装の型計算を使う．既存の二引数補完だけが，推論後に異なる関数型の式を差し込む状態を解消する．

### 4.2 具体的な型の候補

新しい制約を追加せず，型と生成式を一致させる具体案は，定義時の未確定な位置に対して，包装が受け取れる Tensor 型を実際に推論へ反映することである．概略，次の関係を使う．

```text
constant           : Integer -> Integer
包装した constant  : Tensor Integer -> Tensor Integer
ones               : [Tensor Integer] -> [Tensor Integer]
```

これは呼び出し後に `[Integer] -> [Integer]` の型を便宜的に付け替える案ではない．包装後の型を受け手の `map` の引数型と照合し，定義を一般化する前に本体・引数・戻り値へ反映する．その後の挿入器は，この型の違いから同じ包装を復元する．

この型を明示した同等の関数を現行実装で確認したところ，次は両方成功した．

```text
ones [1,2]        → [1,1]       : [Tensor Integer]
ones [[|1,2|]]    → [[|1,1|]]   : [Tensor Integer]
```

`sum` についても，同じ方針なら，元の加算の型クラス制約を要素型に残した `{AddSemigroup a} [Tensor a] -> Tensor a` が検討候補になる．未注釈の `sum` にこの型を自動で推論する変更は，まだ行っていない．

### 4.3 採用前に確かめる型の精度

上記の共通の型では，スカラーだけを渡した `ones [1,2]` にも `[Tensor Integer]` が付く．階数0を許す意味では正しいが，従来の `[Integer]` よりスカラーであるという情報が少ない．この点を隠して「結果型まで完全に解決した」とは扱わない．使用箇所のデータ型でスカラーと確定する既存の直接適用は，現在の精密な型を保つ方針で検討する．

また，一般の関数の入力がスカラーだからといって，出力から Tensor を取り除く改善はできない．`Tensor Integer -> Tensor Integer` でも，常にベクトルを返す関数が存在するためである．

したがって，この共通の型を主要型として採用できるかは，型付け規則全体に対して検証する必要がある．主要型とは，仕様が認めるほかの型を型変数への代入で得られる，最も一般的な型である．正規化を含む主要型性の課題と合わせて解決し，定理の対象を狭めたり，主要型性を決定性に置き換えたりしない．新しい制約を追加する案にも戻らない．

この節は，型と生成式が整合する具体案と，その案でまだ証明すべき点の区別である．全体の主要型性まで成立すると結論した最終仕様ではない．

## 5. 実装する場合の順序と完了条件

1. **明示的な操作の修正**：`tensorMap` のスカラー・未確定の場合，`tensorMap2` のスカラー・混在・未確定の場合にも，関数型を照合し正しい戻り値型を計算する．`Integer -> Bool` のように入力と出力の型が異なる例を回帰テストにする．
2. **適用規則の整理**：正規化，階数0の受入れ，持ち上げによる型の変更を分ける．直接適用と高階引数への挿入で Tensor の付く位置を正しく計算する．リスト・タプルの内部の不一致を結果全体への包装で隠さない．
3. **定義時の補完の一般化**：1・2と共通の型計算を使い，一引数・多引数・部分適用・混在する位置を扱う．定義に保存する型の候補と主要型性の関係を検討し，仕様を確定してから一般化を実装する．
4. **証明との接続**：推論した型と挿入された関数型の一致，階数0の受入れの型保存，包装の任意個数での型保存，推論後の型情報からの挿入成功を示す．

確認する組合せは，直接適用と定義経由，スカラーのみ・Tensor のみ・混在，一引数・二引数・三引数以上，スカラー関数・Tensor 全体を受け取る関数・無制約の恒等関数，リスト結果・タプル結果，正規化，共有添字である．既存の15件の型・挿入テストと実行時の比較も維持する．不適合な要素型を正しく拒否することも検査する．
